# Canvas 列表摘要化：实现与 50 人 A/B 验证

日期：2026-09-10（Asia/Shanghai）。A 基线为 `c0f9642833441029b0e57ced3427eba3d535d6a9`，已包含 media.expires_at 重复写优化。

## 结果

本次将 Canvas 列表与完整文档加载分开，列表不再携带 document。详情、创建、保存、导入仍返回完整文档。50 人 A/B 中，单次列表平均响应从 145,073 字节降至 586 字节（减少 **99.60%**），稳态总响应流量减少 **45.62%**。两组都没有 5xx、异常错误、连接池等待或读回一致性错误。

存在明确代价：列表 p95 从 **12.82 ms 上升到 18.73 ms**，列表 SQL 平均执行时间从 **0.62 ms 上升到 10.04 ms**，PostgreSQL 平均 CPU 从 **6.34% 上升到 11.66%**。本轮达成列表数据量目标，不能描述成数据库查询或列表延迟全面加速。

## 数据与恢复边界

| 数据 | 来源和职责 |
| --- | --- |
| CanvasSummary | id、title、revision、createdAt、updatedAt、nodeCount、connectionCount；用于列表展示和远端目录信息 |
| CanvasProjectDetail | 详情和导入等完整记录，含 document |
| Store.summaries | 远端摘要目录；不含空文档占位 |
| Store.projects | 已加载或本地恢复的完整文档，也是本地图片/视频清理的引用依据 |
| projectSync.serverRevision | 当前本地文档的保存基准；刷新摘要不能更新已有本地文档的这个字段 |

启动过程先恢复本地文档和同步状态，再合并摘要。摘要不会覆盖本地 document、清除 dirty/pending、确认尚未收到回执的保存，也不会触发编辑器历史重置。既有未同步本地画布的导入策略保留，导入结果单独使用完整详情类型。

进入编辑器时按需获取详情；卡片复制、重命名和分享也在操作时加载。列表渲染不逐个读取详情。新建未上传、dirty/pending、保存中、冲突及结果未知的文档优先保留本地版本及其原保存基准。详情失败显示错误与重试，不初始化为空 Canvas。

安全详情加载按账号与项目去重，拒绝账号切换、删除、更新后的目录已移除该项目等情况下的迟到响应。请求期间产生的新编辑不会被响应覆盖。显式“加载服务器版本”仍保留其冲突恢复含义，与普通详情加载分开；同时保护刷新期间的删除，避免迟到 GET 吞掉 pending delete。

初始编辑租约获取改为安全详情加载；首次加载失败后的重试会重新激活编辑状态。离开页面时，即使详情 GET 尚未完成，也会释放持有的 Web Lock。未改变租约归属、冲突刷新和保存协议。

已访问画布的本地完整文档继续保留，因此本轮不是本地文档缓存淘汰。未加载详情不被视为“没有媒体引用”；dirty 文档内的待上传图片和旧本地视频仍受引用保护。服务端媒体权限、引用事务、清理 claim、删除和 5 分钟清理延迟均未修改。

## 后端查询

`ListCanvasProjects` 显式投影元信息，并在 PostgreSQL 中计算 nodes/connections 的 JSON 数组长度。历史缺失、null、非数组字段按 0 计数；不新增计数字段或迁移。

SQL 的结果不包含原始 document，减少 DB→Go 的完整文档传输及 Go/HTTP/浏览器处理的数据量。**PostgreSQL 仍需要读取、解析 document 来计算数量**，不能将响应体缩小等同于数据库不再访问 document，也不能用 HTTP 字节数替代数据库传输字节数。

本次未修改 Workflow、素材分页、Canvas 分页、保存协议、revision/409、幂等键、Undo/Redo 算法或服务端媒体生命周期。

列表响应是一次明确的数据契约变更，正式发布时需配套更新前后端，旧打开的标签页需要刷新以加载新前端。本轮不部署，也不通过空 document 做旧客户端兼容。

## 行为验证

- 后端先验证旧实现仍返回完整 document 和通配查询，再切换摘要投影；覆盖归属隔离、数量、详情与导入完整性。
- 前端覆盖摘要不清 dirty/pending/unknownRequest，不提升本地保存基准；新摘要之后的真实保存仍携带旧 revision 并得到 409。
- 覆盖详情并发去重、请求期间编辑/删除/切换账号、详情失败重试、更新目录移除 ID 后的迟到响应，以及强制刷新期间删除不会被吞掉。
- 覆盖摘要持久化与完整文档的独立恢复，以及真实图片和视频清理仅移除无引用缓存。
- 覆盖仅有摘要时的卡片展示、按需复制/重命名/分享、重复点击、删除成功与删除冲突恢复。未改名称时不能用旧摘要标题覆盖刚加载到的服务器标题；卡片卸载后不继续执行待处理动作。

Chrome 使用独立端口 `42117`、专用测试 schema 和压测 fake API。首次列表请求为 579 字节，展示 30/150/250 节点三张卡片，未触发任何逐卡详情 GET。重命名、复制和打开分享对话框才获取相应详情。新增文本→Undo→Redo→再次新增→缩放至 67%→立即返回→刷新后，读回为 32 节点、29 连线、viewport.k=0.67；重新进入编辑器显示两个新增文本及 67%。本轮创建的测试副本删除后未重新出现。

浏览器检查未调用生成接口，也未向真实用户发送分享。压力测试素材为元数据夹具；本轮不据此声明验证了真实 OSS 图片解码或供应商生成。

## A/B 环境与口径

A、B 顺序运行，每次新建独立 PostgreSQL 容器与 schema；共享相同夹具、随机种子 1000 和负载脚本。每次 50 用户，30 秒升压、180 秒稳态、30 秒降压，再完成读回和恢复期观察。50% 浏览、30% Canvas 编辑、20% Workflow 操作，保存间隔 2～5 秒，另有 10 轮同 revision 双客户端竞争。

每人 3 张 Canvas（30/150/250 节点）、200 条素材元数据、5 文件夹、12 节点 Workflow、7 个输出、10 条历史运行。Workflow 使用进程内 fake provider，网络出口限制为该测试进程自身；不调用收费服务。

环境：Apple M1 Pro，10 核、32 GiB；Docker VM 10 CPU、7.75 GiB；PostgreSQL 17 容器限制 2 CPU、1 GiB；原生 Go 1.26.6 / darwin-arm64 / GOMAXPROCS=4，连接池 20 open / 10 idle / 30m lifetime。普通开发应用未重建、未重启。

- API 百分位、响应字节：180 秒稳态的正常业务请求，nearest-rank；401/403/409 等预期业务结果另列。
- Go CPU：进程累计 user+system CPU 差/观测时长，100% 为一核；RSS/数据库 CPU 为抽样，资源窗口包含升压、稳态及降压后的短暂观察。
- 列表 SQL 时间：pg_stat_statements 中列表查询聚合，属于数据库执行时间，不含网络传输与 Go 序列化；不是每条 SQL 的 p95/p99。
- 此为共享开发机上的单次 A/B，不是生产容量或延迟承诺。闭合用户循环可能完成不同请求数，须同时看单次字节数和总字节数。

两组回读均为 151 张 Canvas（含冲突测试项目）、50 个 Workflow、540 个完成的运行（含预置运行），280 个 fake 任务成功。revision 不匹配、输出数量错误、输出媒体缺失、归属错误、重复 attempt 均为 0；媒体审计计数相同。前项优化也保持有效：两组 `expires_at` UPDATE 都为 0。

**性能判断：** 响应体与总流量明显减少；本机 Go 平均 CPU 下降约 9.23%，RSS 峰值仅从 36.23 MiB 变为 36.08 MiB，不能据此宣称显著节省服务端内存。首屏浏览器接收的列表 JSON 同步缩小，但没有采集浏览器堆内存或 JSON parse 时间；已有本地完整文档缓存仍保留，不宣称其被清空。

列表 SQL 的平均时间增至约 16.15 倍，新增节点/连线计数将解析成本放到了数据库；当前表达式有多处 `document::jsonb` 转换，存在重复解析的优化空间。该原因由查询形态推断，未进一步用算子级 profiling 分摊 CPU。`shared_blks_hit` 从 15,179 增至 48,690，不能把它当作实际磁盘读取字节或 DB→Go 传输字节；本轮未独立采集这两类字节数。

本次先保留“不新增字段、由 SQL 计算数量”的约定，未继续调整数据库架构。后续如要降低数据库成本，先独立比较 JSON 计数表达式与执行计划；是否持久化计数应另立方案。当前 50 用户场景仍无超时或连接池等待，但每用户只有 3 张 Canvas，不能据此保证每用户成百上千张画布时相同表现，也不将其扩展为生产安全容量承诺。


## 复现与证据

复用 `scripts/loadtest/run.sh`、`cmd/loadtest` 及其 monitor/summary/consistency 工具。分别在基线和本次代码版本编译压测入口，按顺序运行：

```sh

go build -o /tmp/canvas-summary-after ./cmd/loadtest  # 在本次版本中

LOADTEST_USERS=50 LOADTEST_BINARY=/tmp/canvas-summary-after bash scripts/loadtest/run.sh /tmp/canvas-summary-ab-after
```

每次输出目录必须为空。脚本自行创建和清理专用测试容器，不向正在运行的应用或生产数据库压测。可长期复核的证据随本次修改保存：

- [A/B 结果 JSON](canvas-summary-2026-09-10-results.json)：各 API、SQL、资源、隔离/一致性及二进制 SHA-256。
