# Canvas 保存中刷新：请求恢复修复方案

日期：2026-09-17。状态：待实施，本文件仅描述修复方案；未修改应用代码或生产数据。

## 1. 问题与原因

### 1.1 已确认的现场

生产版本 `3bacd068506553735cc4b4e828710bb3234db315`，用户“江振忠”，画布“平铺/挂拍”（`KLt9Uramk3M0YB1z4CC5y`）。以下时间均为北京时间：

| 时间 | 证据 | 结论 |
| --- | --- | --- |
| 2026-09-17 14:21:22 | 数据库保存记录：请求 `50dee789-62b2-48f8-a4ea-4592491dcd8b`，基础版本 994，结果版本 995 | 原请求已成功提交数据库 |
| 同一秒 | 网关记录画布页面 GET；原 PUT 返回 499，而应用日志对应 PUT 为 200 | 页面重新加载，客户端断开；服务端成功不等于浏览器已收到确认 |
| 14:21:23 | 新请求 `e2ec3a02-be7e-45b5-9947-82c68f0f89fa`，请求序号 1，基础版本 994，服务器版本 995，返回 409 | 新页面没有复用原请求身份，旧版本写入被正确拦截 |

日志能确认页面重新加载，不能区分手动刷新与重新进入页面。调查时服务端画布仍为 v995；不能据此认定冲突后的浏览器草稿也已保存。

### 1.2 代码缺口

主要调用链：

- `web/src/app/(user)/canvas/stores/use-canvas-store.ts`：`saveProject` 创建请求、持久化同步状态、发送请求及处理响应。
- 同文件 `sanitizeStoredCanvasValue`：重新加载时把 `saving` 转为待保存。
- 同文件 `ensureProjectDetail`：保留未同步的本地草稿，不以远端内容直接覆盖。
- `service/canvas_projects.go`、`repository/canvas_project.go`：根据请求 ID、用户、画布、基础版本及内容摘要识别已成功的同一次保存。

目前发送前会等待已有本地写入，但请求快照 `unknownRequest` 仅在网络异常进入 `catch` 后记录。发送和响应之间若页面退出，异常处理可能没有执行机会，浏览器留下的是旧版本和待保存标记，没有原请求的完整身份。

重新进入后，保留草稿本身是正确的；错误在于把未确认的原请求当作一次新保存，生成新 ID。服务器无法匹配已经完成的请求，返回真实的版本差异。修复应补齐前端请求恢复，不放松服务器版本校验。

## 2. 修复目标与约束

1. 每个已有画布的 PUT 在发送前，持久保存请求 ID、基础版本、标题和实际提交文档。
2. 刷新、关闭后重开、断网或响应丢失时，先确认同一次请求，再保存后续修改。
3. 恢复过程中允许继续编辑；最新草稿与未确认请求快照分开，不相互覆盖。
4. 本地编辑不递增 `serverRevision`；只有与当前请求匹配的服务端确认才推进已确认版本。
5. 同一画布保存串行执行，不因自动保存、重试或恢复入口重复启动请求。
6. 保留多端冲突、只读、账号隔离及媒体权限保护。不强制覆盖、不自动重放图片生成任务。

范围为“我的画布”已有画布的保存和恢复；不扩展为 Workflow 通用保存重构，不修改新建接口、删除接口或生成计费协议。需要回归保存期间删除、新建响应丢失等现有相邻行为。

## 3. 修复方案

### 3.1 复用现有持久化结构

沿用现有按用户隔离的 Canvas 存储及 `CanvasProjectSync.unknownRequest`，将其含义明确为“尚未确认的保存请求”，包含准备发送与结果不明两种情况。不新增后端表、字段或接口，也不另建一套本地请求队列。

| 数据 | 内容 | 更新规则 |
| --- | --- | --- |
| 最新草稿 | 当前标题、节点、连接、遮罩引用、视口等 | 用户操作持续更新并按现有方式持久化 |
| `serverRevision` | 当前会话已确认的服务器版本 | 不随本地保存自行增加 |
| 未确认请求 | 原 trace/request ID、基础版本、标题、提交文档 | 创建后不可变；重试不改 ID、版本或内容 |
| 临时运行状态 | in-flight、当前会话/操作身份 | 只用于串行调度和旧回调隔离 |

请求快照取自经过现有序列化清理的实际 PUT 内容，并与后续可变草稿分离；不包含 Blob URL、图片二进制或临时显示状态。读取历史快照时保留其原内容，不借恢复过程把它改成最新草稿。

### 3.2 发送前登记并等待写入

已有画布的一次保存按以下顺序执行：

1. 检查账号、编辑权、冲突状态和当前画布的 in-flight 标记。
2. 同步占用当前画布的 in-flight 名额，防止等待本地写入期间另一个入口进入。
3. 有未确认请求则复用；否则从当前草稿创建不可变请求快照，写入 `unknownRequest`。
4. 等待包含该快照的本地持久化成功，再允许发出网络请求。等待的是已登记快照的写入屏障，不应因持续编辑而无限等待所有后续写入。
5. 等待后重新检查账号、页面/操作身份、编辑权和目标是否仍有效；失效则不发送，保留必要恢复依据。
6. 发送已登记快照，使用其中的原请求 ID、基础版本、标题和内容。

本地写入失败时不得调用服务器，保留内存草稿并显示本地保存失败，允许重试。不能只设置内存状态后立即发送，也不能依赖 `beforeunload` 或 `pagehide` 才补记录。

复用现有持久化队列；若需要调整屏障，只返回已登记写入对应的 Promise，不重写存储层。已有 projects/sync 分开写入的结构应保持写入顺序；通过故障注入验证任意写入边界中断不会丢失原请求或把新草稿替换成旧内容。

### 3.3 重新进入与新编辑

完成本地恢复并取得编辑权后：

- 有有效未确认请求：优先重发原请求。成功过则服务器返回原结果；尚未成功且基础版本仍有效则执行一次。
- 用户继续编辑：只更新最新草稿，暂不发送后续 PUT，也不修改未确认请求内容。
- 网络仍不可用或结果仍不明：保留快照，沿用现有网络重试入口，不持续制造新请求 ID。
- 响应被接受后：确认原请求，基于返回版本判断是否仍有新草稿需要保存；有则创建新请求。

示例：

```text
已确认 v994
  → 登记请求 A（移动图片，baseRevision=994）
  → 服务器已保存 v995，但刷新使响应丢失
  → 新页面恢复 A；用户继续添加文字，最新草稿包含两项修改
  → 重发原 A，服务器返回其已完成结果 v995
  → 仅确认 A，不把 A 的旧文档写回编辑器
  → 创建请求 B（最新草稿，baseRevision=995）
  → B 成功，已确认版本更新为 v996
```

本地草稿的“已持久保存”与服务器的“已确认 v995”是两种状态，不能混用一个版本号。

### 3.4 成功确认与迟到响应

- 确认处理必须匹配当前账号、画布、会话/操作身份和未确认请求 ID。请求已被确认、替换或失效的旧回调，不得清除新的请求快照。
- 不用响应中的旧标题、节点、连接、视口替换最新草稿。列表摘要也不能被更旧响应覆盖。
- 清除 A 的未确认记录与确认其版本在同一次同步状态更新中完成，并等待确认状态持久化后释放保存流程，让 B 继续。
- 若服务器确认成功但本地确认写入失败，保留或恢复 A 的待确认状态并提示错误，不启动 B；重新进入可安全重放 A。
- 旧确认不得降低版本；但不能简单取 `max(本地版本, 响应版本)` 后自动提交。若较新版本来自其他会话，它不代表当前草稿已经与之合并，应保留冲突处理。
- A 的去重回执只证明 A 曾保存为 v995，不证明远端现在仍是 v995。若其他页面已推进为 v996，下一次基于 v995 的 B 应正常收到 409，不能覆盖他人修改。
- 保存期间用户删除画布时，不得因 A 返回成功而复活本地画布；按现有删除队列顺序处理。账号切换、只读接管或旧会话回调同样不能写回新会话状态。

### 3.5 错误、历史与保留期

| 情况 | 处理 |
| --- | --- |
| 网络超时、断连、无法确认是否提交的服务端异常 | 保留原快照，重放同一请求 |
| 明确参数/权限错误 | 显示现有错误，不无限重试；保留草稿。只处理当前匹配请求，不误清除后来操作 |
| 409 版本冲突 | 停止自动保存，保留草稿及冲突信息；不自动把版本加一后覆盖 |
| 旧版 `saving=true` 但没有请求快照 | 无法恢复已经丢失的请求 ID；先读取远端核对。版本相同时可创建新保存；版本不同则保留草稿并进入冲突处理 |
| 快照损坏或缺少关键字段 | 保留草稿并显示恢复错误，不编造原请求内容重放 |
| 本地缓存已清除、换浏览器或换设备 | 无法保证恢复未持久化/已丢失的草稿或请求身份 |

服务器 `canvas_save_requests` 的保留规则为 24 小时，实际删除由现有定期任务执行。本次不延长保留期：记录仍在时可去重；已被清理时，原基础版本仍由服务器校验，版本不一致就安全地停在 409。不能承诺任意时长离线后都能无冲突恢复。

此次现场已经发生在旧实现上，新代码不能凭空重建丢失的 A。现场恢复应先保护当前浏览器草稿，再比较远端文档，不直接清缓存或用远端副本覆盖。

## 5. 测试与验收

### 5.1 自动化行为测试

用可控 Promise、持久化快照和同步屏障构造真实先后关系。模拟刷新必须创建全新的 Store、重新读取已落盘数据，不能仅在原 Store 上再次调用保存；不能只用固定 sleep 模拟竞态。

| 场景 | 必须断言 |
| --- | --- |
| 发送前本地写入被阻塞 | API 调用为 0；屏障释放后才发送，ID/版本/内容与落盘快照一致 |
| 快照本地写入失败 | 不请求服务器，草稿保留且错误可见 |
| 多个保存入口在屏障期间同时进入 | 同一画布最多一个请求，只有一份当前未确认快照 |
| 持久化完成、网络尚未发送就退出 | 新 Store 重放同一请求，服务器仅执行一次 |
| 服务端提交成功，响应未交付即退出 | 用新 Store 重放原 ID 和原内容；只增加一次版本，无 409 |
| 恢复 A 期间继续编辑并落盘 | 草稿保留新增节点、连接、位置、标题及视口；A 的内容不变，B 等待 A 确认后以正确版本提交 |
| 重放 A 再次中断并刷新 | 仍保持同一请求 ID 和内容，不制造第三份逻辑保存 |
| A 成功，但确认状态本地写入失败 | 不启动 B；恢复 A 不丢新草稿、不重复增加版本 |
| B 已确认后注入迟到 A 回调 | 不回退版本、不覆盖草稿/摘要、不清除新的待确认请求 |
| 新会话、账号切换、丢失编辑权 | 旧回调不能写入当前会话；等待期间失效的请求不被发送 |
| 保存期间删除画布 | 原确认不复活画布，删除使用正确基线并保持原有冲突规则 |
| 旧存储没有快照、快照损坏 | 安全保留草稿；不盲目重放或悄悄覆盖远端 |
| 持续快速编辑与大文档 | 网络可在已登记快照落盘后发起，不被持续写入饿死；不每次编辑复制所有历史文档 |

服务端复核使用隔离 PostgreSQL 和独立连接：

- 相同用户/画布/请求 ID/内容并发提交：一个实际版本更新，两方得到一致回执。
- 同请求 ID 但内容、基础版本、用户或画布不同：拒绝，不误判成功。
- A 成功后其他会话保存 C，再重放 A：返回 A 的原回执但不回滚远端；随后基于 A 版本的 B 被 409 拒绝。
- A 回执清理后重放：已变化的版本仍拒绝；不产生重复覆盖。

### 5.2 浏览器验证

在本地隔离页面中拦截并模拟 API，使用实际浏览器存储：

1. 延迟 PUT 响应，模拟服务器已经接受，随后重新加载页面。
2. 页面恢复时继续编辑，核对 A 重放、B 串行以及最终文档和版本。
3. 关闭页面后在同一浏览器上下文重开，验证恢复；并覆盖离线后恢复网络。
4. 两标签页编辑权交接、只读页面、账号切换及冲突提示。
5. 本地写入失败、缺失快照的旧缓存和重复刷新。

验证请求体、请求 ID、实际服务端写入次数及最终草稿，不能只检查界面显示“已保存”。不连接生产数据库、OSS，不调用图片或视频生成接口。

### 5.3 检查与交付门槛

- 前端相关 Store、同步及编辑权 Bun 测试；全量 Bun 测试、`bun run typecheck`、`bun run build`。
