# Canvas 保存中刷新：请求恢复修复方案

日期：2026-09-17。状态：审查后修订，待实施。本次仅更新方案，不修改应用代码或生产数据。

修订重点：补齐本地草稿与同步状态的原子持久化、Service 层幂等查询竞态，以及明确拒绝后解除旧请求阻塞的规则。

### 1.2 代码缺口

主要调用链：

- `web/src/app/(user)/canvas/stores/use-canvas-store.ts`：`saveProject` 创建请求、持久化同步状态、发送请求及处理响应。
- 同文件 `sanitizeStoredCanvasValue`：重新加载时把 `saving` 转为待保存。
- 同文件 `ensureProjectDetail`：保留未同步的本地草稿，不以远端内容直接覆盖。
- `service/canvas_projects.go`、`repository/canvas_project.go`：根据请求 ID、用户、画布、基础版本及内容摘要识别已成功的同一次保存。

目前发送前会等待已有本地写入，但请求快照 `unknownRequest` 仅在网络异常进入 `catch` 后记录。发送和响应之间若页面退出，异常处理可能没有执行机会，浏览器留下的是旧版本和待保存标记，没有原请求的完整身份。

重新进入后，保留草稿本身是正确的；错误在于把未确认的原请求当作一次新保存，生成新 ID。服务器无法匹配已经完成的请求，返回真实的版本差异。修复应补齐前端请求恢复，不放松服务器版本校验。

## 2. 修复目标与约束

1. 每个已有画布的 PUT 在发送前，持久保存请求 ID、基础版本、标题和实际提交文档。
2. 刷新、关闭后重开、断网或响应丢失时，先确认同一次请求，再保存后续修改。
3. 恢复过程中允许继续编辑；最新草稿与未确认请求快照分开，不相互覆盖。
4. 本地编辑不递增 `serverRevision`；只有与当前请求匹配的服务端确认才推进已确认版本。
5. 同一画布保存串行执行，不因自动保存、重试或恢复入口重复启动请求。
6. 本地已提交的草稿与对应同步状态一致；不得恢复出“新草稿 + 旧的已同步标记”。
7. Service 完整入口在相同请求交错执行时仍正确去重；真实版本冲突继续拒绝。
8. 明确拒绝后允许修正再保存；权限失效或结果不明时保留必要请求身份。
9. 保留多端冲突、只读、账号隔离及媒体权限保护。不强制覆盖、不自动重放图片生成任务。

范围为“我的画布”已有画布的保存和恢复，包括 Canvas 专用本地持久化、PUT 保存和幂等错误处理。不扩展为 Workflow 通用保存重构，不修改新建接口、删除接口或生成计费协议。需要回归保存期间删除、新建响应丢失、本地上传预览等现有相邻行为。

## 3. 修复方案

### 3.1 复用现有持久化结构

沿用现有按用户隔离的 Canvas 存储及 `CanvasProjectSync.unknownRequest`，将其含义明确为“尚未确认的保存请求”，包含准备发送与结果不明两种情况。不新增后端表、数据库字段或接口，也不另建一套本地请求队列。仅在现有 PUT 错误响应需要区分语义时，复用现有 `data.code` 扩展稳定错误码，保持响应外层结构和 HTTP 状态含义。

| 数据 | 内容 | 更新规则 |
| --- | --- | --- |
| 最新草稿 | 当前标题、节点、连接、遮罩引用、视口等 | 用户操作持续更新并按现有方式持久化 |
| `serverRevision` | 当前会话已确认的服务器版本 | 不随本地保存自行增加 |
| 未确认请求 | 原 trace/request ID、基础版本、标题、提交文档 | 创建后不可变；重试不改 ID、版本或内容 |
| 临时运行状态 | in-flight、当前会话/操作身份 | 只用于串行调度和旧回调隔离 |

请求快照取自经过现有序列化清理的实际 PUT 内容，并与后续可变草稿分离；不包含 Blob URL、图片二进制或临时显示状态。读取历史快照时保留其原内容，不借恢复过程把它改成最新草稿。核对 API 层现有再次清理文档的行为，确保首次提交和重放的实际请求体一致；无法原样恢复时显示恢复错误，不偷偷迁移快照后继续使用原 ID。

### 3.2 本地原子持久化与发送屏障

#### 3.2.1 草稿与同步状态作为一份本地提交

采用 **Canvas 专用 IndexedDB 原子写入**，不继续依赖 `projects → summaries → sync` 分别提交的顺序，也不新增一套持久化日志：

1. 对会改变服务端文档的本地操作，在同一次 Store 更新中修改草稿及 `dirty/pending`。保存调度放在这次更新之后，避免队列先收到“新草稿 + clean”的中间状态。标题、节点、连接、视口等修改均遵守此规则。
2. 继续使用现有 IndexedDB 数据库、`canvas_documents` object store、按用户隔离的 Key 和 JSON 结构；同一份状态中需要变更的 `projects/sync/summaries` 在一个 `readwrite` 事务内提交。
3. JSON 序列化在事务外完成；事务内仅发起本地读写，不等待网络或其他异步预处理。必须等 `transaction.oncomplete` 才报告写入成功，不能以单个 `put` 成功作为整份提交成功。
4. 事务失败或页面在提交前退出，保留上一份完整状态；事务成功则整份新状态可恢复。文档缓存的“已经写入”引用也只在事务完成后更新，失败时必须允许重写。
5. 保留现有按引用跳过未变化文档序列化的优化。仅同步状态变化时，不重复写整个画布集合；没有服务端文档变化的本地上传进度仍保持原同步语义。

`localforage.setItem` 的多个调用并不构成同一事务。实施时仅为 Canvas 持久化增加所需的批量事务读写原语，并沿用同一数据库的连接、版本和升级约束；不修改其他业务存储、不新增依赖、不调用 localforage 私有内部字段。恢复时也在一个只读事务中取得相关 Key，避免恰逢提交时拼出两份不同状态。旧合并 Key 的读取兼容继续保留。

新协议只保证已经完成本地事务提交的数据可恢复；尚未落盘、仅存在于内存的最后一次编辑不能承诺跨崩溃恢复。历史版本已经留下的“草稿/同步标记不一致”也不能凭空识别，应保护现场草稿后核对，不宣称能自动修复所有旧缓存。

#### 3.2.2 请求登记完成后才允许发送

已有画布的一次保存按以下顺序执行：

1. 检查账号、编辑权、冲突状态和当前画布的 in-flight 标记。
2. 同步占用当前画布的 in-flight 名额，防止等待本地写入期间另一个入口进入。
3. 有未确认请求则复用；否则从当前草稿创建不可变请求快照，写入 `unknownRequest`。登记请求与本次保存状态使用同一次 Store 更新。
4. 取得并等待包含该快照的本地事务对应的 Promise，再允许发出网络请求。等待固定的这次写入屏障，不追逐持续编辑带来的后续写入。
5. 等待后重新检查账号、页面/操作身份、编辑权、冲突状态及目标是否仍有效；失效则不发送，保留必要恢复依据，并释放本次占用。
6. 发送已登记快照，使用其中的原请求 ID、基础版本、标题和内容。

本地写入失败时不得调用服务器，保留内存草稿并显示本地保存失败，允许重试。不能只设置内存状态后立即发送，也不能依赖 `beforeunload` 或 `pagehide` 才补记录。

复用现有持久化队列，限定改动为 Canvas 所需的原子读写、固定写入屏障和状态合并，不重写整个 Zustand 或图片缓存层。队列中的确认提交与后续草稿提交保持顺序；任何错误分支都必须释放本次 in-flight，且不得错误地启动后续 PUT。

### 3.3 重新进入与新编辑

完成本地恢复并取得编辑权后：

- 有有效未确认请求：优先重发原请求。成功过则服务器返回原结果；尚未成功且基础版本仍有效则执行一次。
- 用户继续编辑：只更新最新草稿，暂不发送后续 PUT，也不修改未确认请求内容。
- 网络仍不可用或结果仍不明：保留快照，沿用现有网络重试入口，不持续制造新请求 ID。
- 响应被接受后：确认原请求，基于返回版本判断是否仍有新草稿需要保存；有则创建新请求。

示例：

```text
已确认 v994
  → 登记请求 A（移动图片，baseRevision=994）
  → 服务器已保存 v995，但刷新使响应丢失
  → 新页面恢复 A；用户继续添加文字，最新草稿包含两项修改
  → 重发原 A，服务器返回其已完成结果 v995
  → 仅确认 A，不把 A 的旧文档写回编辑器
  → 创建请求 B（最新草稿，baseRevision=995）
  → B 成功，已确认版本更新为 v996
```

本地草稿的“已持久保存”与服务器的“已确认 v995”是两种状态，不能混用一个版本号。

### 3.4 成功确认与迟到响应

- 确认处理必须匹配当前账号、画布、会话/操作身份和未确认请求 ID。请求已被确认、替换或失效的旧回调，不得清除新的请求快照。
- 不用响应中的旧标题、节点、连接、视口替换最新草稿。列表摘要也不能被更旧响应覆盖。
- 清除 A 的未确认记录、确认其版本以及判断最新草稿是否仍待保存，在同一次 Store 更新和本地原子提交中完成，并等待提交完成后释放保存流程，让 B 继续。若用户在确认写入期间继续编辑，后续排队状态必须包含该编辑，且保存调度不得遗漏。
- 若服务器确认成功但本地确认写入失败，保留或恢复 A 的待确认状态并提示错误，不启动 B；重新进入可安全重放 A。
- 旧确认不得降低版本；但不能简单取 `max(本地版本, 响应版本)` 后自动提交。若较新版本来自其他会话，它不代表当前草稿已经与之合并，应保留冲突处理。
- A 的去重回执只证明 A 曾保存为 v995，不证明远端现在仍是 v995。若其他页面已推进为 v996，下一次基于 v995 的 B 应正常收到 409，不能覆盖他人修改。
- 保存期间用户删除画布时，不得因 A 返回成功而复活本地画布；按现有删除队列顺序处理。账号切换、只读接管或旧会话回调同样不能写回新会话状态。

### 3.5 明确拒绝、权限失效与结果不明

“尚未确认”不等于“必须永远重放”。请求结束或暂停必须依据可验证的服务端语义，而非报错文案或仅凭 HTTP 4xx。

| 情况 | 原请求与草稿的处理 | 后续保存 |
| --- | --- | --- |
| 网络超时、断连、无法确认是否提交的服务端异常 | 保留原快照和最新草稿 | 恢复网络后重放原请求，不生成新 ID |
| 可以确认该逻辑请求未受理的参数/引用校验拒绝 | 只结束当前匹配请求，原子清除其 `unknownRequest`；保留草稿、原已确认版本和可见错误 | 不立即自动重发同一失败内容；用户修正后或主动重试时创建新请求 |
| 401/403、身份或编辑权失效 | 暂停发送，保留原请求和草稿；不因为当前尝试被拒绝就认定原尝试一定未提交 | 同一账号恢复权限、取得编辑权后先确认原请求；不同账号不得接管 |
| 409 真实版本冲突 | 停止自动保存，保留草稿、请求和冲突信息 | 沿用冲突处理，不自动递增版本或覆盖 |
| 请求 ID 与原回执的内容/用户/画布/基础版本不匹配 | 显示请求身份恢复错误并保留草稿；不把它当作普通参数拒绝 | 禁止自动换 ID 绕过；先核对恢复状态 |
| 无法分类的 HTTP 错误或旧服务端缺少拒绝标识 | 保留快照，按结果不明或需要确认处理 | 不自动清除身份，也不无限快速重试 |

服务端继续负责识别明确未受理，前端只处理稳定语义。沿用现有 `{code, data, msg}` 响应及 `ApiRequestError.data`；PUT 可在 `data.code` 中区分 `canvas_save_rejected` 与 `canvas_save_request_mismatch`，继续保留现有 `canvas_revision_conflict`。不把通用 `code=1`、`SafeMessage`、所有 400/413 或中文关键词当作“未受理”证据。

明确拒绝标识只用于能够确认未更新画布的校验/事务回滚结果，并先排除已匹配成功回执。对曾经结果不明的重放，当前校验失败不天然证明原请求未提交；无法核清原结果时保留快照和错误，不下发“可丢弃原请求”的结论。该标识只扩展 Canvas PUT，不改变创建、删除或供应商错误契约。旧前端继续看到原有 HTTP 错误和安全文案。

拒绝状态处理也必须经过固定的持久化屏障。清除请求的本地提交失败时，保留可恢复的 A，不启动 B。用户在 A 返回拒绝前已改好的草稿继续保留，但不因失败回调立即无条件循环提交；由修正后的保存入口或显式重试启动后续请求。确认失败、权限恢复、刷新后均采用相同规则，旧回调不能清除新请求。

必须覆盖：A 的无效内容被明确拒绝 → 草稿仍在 → 修正内容 → B 使用新 ID、原已确认基础版本 → B 成功。B 不得继续使用 A 的旧内容或 ID，也不得仅因结束 A 就增加版本。

### 3.6 修复 Service 层幂等查询竞态

现有 Repository 事务已经使用请求 ID 唯一约束及回执校验。需要修复的是其外层 Service 的提前返回，不新增表或放松去重条件。

确定需要覆盖的交错：

```text
重放 A：第一次查询回执，尚不存在
原请求 A：事务提交，回执与画布 v995 一起可见
重放 A：查询画布得到 v995，与 baseRevision=994 不同
当前行为：在进入 Repository 幂等事务前返回 409
目标行为：核对刚提交的 A 回执，返回 A 原来的成功结果
```

优先采用最小改动：在 Service 将要因版本不同返回 409 时，重新查询并核对同一请求回执；若匹配则返回原结果，若身份或内容不匹配则拒绝，若仍无匹配回执则保留真实冲突。项目不存在的提前返回也核对同一回执，保持既有“回执证明曾保存成功”的语义；回执不会重新创建或复活已删除的服务端画布。

复用同一份回执匹配规则：用户、画布、标准化请求 ID、基础版本、内容摘要必须全部一致。保存事务完成时画布与回执原子提交，因此读到原请求造成的新版本后，后续回执查询应能读到对应记录；若已经超过保留期且回执被清理，仍按真实版本校验安全拒绝。

保留 Repository 的事务内去重与版本校验，继续覆盖“两个请求都读到旧版本后才进入事务”的交错。不能只在前端收到 409 后不断重试，也不能跳过媒体引用、合法历史图兼容或用户权限检查。

### 3.7 历史缓存与保留期

| 情况 | 处理 |
| --- | --- |
| 旧版 `saving=true` 但没有请求快照 | 无法恢复已丢失的请求 ID；先读取远端核对。版本相同时可创建新保存，版本不同则保留草稿并进入冲突处理 |
| 快照损坏或缺少关键字段 | 保留草稿并显示恢复错误，不编造原请求内容重放 |
| 本地缓存已清除、换浏览器或换设备 | 无法保证恢复未持久化/已丢失的草稿或请求身份 |

服务器 `canvas_save_requests` 的保留规则为 24 小时，实际删除由现有定期任务执行。本次不延长保留期：记录仍在时可去重；已被清理时，原基础版本仍由服务器校验，版本不一致就安全地停在 409。不能承诺任意时长离线后都能无冲突恢复。

此次现场已经发生在旧实现上，新代码不能凭空重建丢失的 A。现场恢复应先保护当前浏览器草稿，再比较远端文档，不直接清缓存或用远端副本覆盖。

## 5. 测试与验收

### 5.1 自动化行为测试

用可控 Promise、持久化快照和同步屏障构造真实先后关系。模拟刷新必须创建全新的 Store、重新读取已落盘数据，不能仅在原 Store 上再次调用保存；不能只用固定 sleep 模拟竞态。

| 场景 | 必须断言 |
| --- | --- |
| 草稿及置脏提交之间模拟崩溃 | 原子提交前为上一份完整状态，提交后为“新草稿 + 正确待保存状态”；不得恢复出“新草稿 + clean” |
| 一个事务中前几次 put 成功、最后一次失败 | 整个事务回滚；已写入缓存引用不前进，重试必须实际重写 |
| 本地读取与另一份提交交错 | 恢复结果来自同一次完整状态，不混合新旧 projects/sync |
| 发送前本地写入被阻塞 | API 调用为 0；屏障释放后才发送，ID/版本/内容与落盘快照一致 |
| 快照本地写入失败 | 不请求服务器，草稿保留且错误可见 |
| 多个保存入口在屏障期间同时进入 | 同一画布最多一个请求，只有一份当前未确认快照 |
| 持久化完成、网络尚未发送就退出 | 新 Store 重放同一请求，服务器仅执行一次 |
| 服务端提交成功，响应未交付即退出 | 用新 Store 重放原 ID 和原内容；只增加一次版本，无 409 |
| 恢复 A 期间继续编辑并落盘 | 草稿保留新增节点、连接、位置、标题及视口；A 的内容不变，B 等待 A 确认后以正确版本提交 |
| 重放 A 再次中断并刷新 | 仍保持同一请求 ID 和内容，不制造第三份逻辑保存 |
| A 成功，但确认状态本地写入失败 | 不启动 B；恢复 A 不丢新草稿、不重复增加版本 |
| B 已确认后注入迟到 A 回调 | 不回退版本、不覆盖草稿/摘要、不清除新的待确认请求 |
| 新会话、账号切换、丢失编辑权 | 旧回调不能写入当前会话；等待期间失效的请求不被发送 |
| 保存期间删除画布 | 原确认不复活画布，删除使用正确基线并保持原有冲突规则 |
| 明确拒绝后修正并重试 | A 请求记录结束、草稿保留、版本不变；B 使用新 ID 和修正内容成功保存 |
| 拒绝处理的本地确认失败 | A 的恢复依据保留，B 不发送；重新进入后不丢修正草稿 |
| 权限失效、未知 4xx、身份不匹配 | 不误判明确未受理，不自动清除原请求或换 ID；权限恢复后核对原请求 |
| 旧存储没有快照、快照损坏 | 安全保留草稿；不盲目重放或悄悄覆盖远端 |
| 持续快速编辑与大文档 | 网络可在已登记快照落盘后发起，不被持续写入饿死；不每次编辑复制所有历史文档 |

服务端验证使用隔离 PostgreSQL、独立连接和可控同步屏障，必须调用完整 `service.UpdateCanvasProject`，并覆盖 Handler 错误码。不能只验证 Repository，不能用固定 sleep 代替交错控制：

- 重放 A 查回执未命中后暂停 → 原 A 提交完成 → 放行重放 A 读取新版本：必须返回原成功回执，不能 409；实际版本只增加一次。
- 两个请求均通过 Service 的旧版本检查，再进入事务：仍只更新一次，两方得到一致回执。
- 相同用户/画布/请求 ID/内容并发提交：一个实际版本更新，两方得到一致回执。
- 同请求 ID 但内容、基础版本、用户或画布不同：拒绝，不误判成功。
- A 成功后其他会话保存 C，再重放 A：返回 A 的原回执但不回滚远端；随后基于 A 版本的 B 被 409 拒绝。
- A 回执清理后重放：已变化的版本仍拒绝；不产生重复覆盖。
- A 成功后画布被删除，再重放 A：回执按既有语义返回，不重新创建画布；后续保存仍遵守删除及冲突规则。
- 明确校验拒绝/确定回滚、权限失效、回执身份不匹配和提交结果不明分别返回正确语义；不能把全部 400 或可见文案归为明确拒绝。
- 合法历史画布、媒体权限与引用状态不因竞态修复被跳过或更严格地误拒。

### 5.2 浏览器验证

在本地隔离页面中拦截并模拟 API，使用实际浏览器存储：

1. 延迟 PUT 响应，模拟服务器已经接受，随后重新加载页面。
2. 页面恢复时继续编辑，核对 A 重放、B 串行以及最终文档和版本。
3. 关闭页面后在同一浏览器上下文重开，验证恢复；并覆盖离线后恢复网络。
4. 两标签页编辑权交接、只读页面、账号切换及冲突提示。
5. 本地事务中止、磁盘写入失败、缺失快照的旧缓存和重复刷新；检查实际 IndexedDB，不能只用“批量写函数被调用”的断言代替。
6. 参数明确拒绝后修改草稿并重试、权限恢复后重放，以及拒绝提示期间刷新。
7. 上传中的本地图片预览仍可恢复，临时节点不会被错误序列化进 PUT；本次请求恢复不触发任何生成接口。

验证请求体、请求 ID、实际服务端写入次数及最终草稿，不能只检查界面显示“已保存”。不连接生产数据库、OSS，不调用图片或视频生成接口。
